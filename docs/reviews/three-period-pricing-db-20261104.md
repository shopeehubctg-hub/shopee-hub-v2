## Approved canonical price representation

1. Preserve the existing database price types. Treat `pricingPeriod` as a separate stable Calculator/business identifier: e.g. all_days, normal_all, normal_1_15, campaign, normal_16_end. Do not use translated labels, display names, scenario array position or serviceScenario alone as keys.
2. Version settings include an explicit mode: uniform / normal_campaign / split_normal. Server validators must enforce the exact permitted period identities/cardinality for each mode, reject duplicate or missing identities, and preserve v1 reads. Existing exportSnapshots requires exactly2 scenarios and deduplicates serviceScenario; it must become a shared version/mode-aware validator used by export, import, single creation, batch, repricing and History.
3. Finite selected months/custom date windows can materialize clipped, non-overlapping Normal rows for days1–15 and16–month-end. Handle February/leap years, partial months, multi-month and year boundaries. An explicit saved mapping must retain which business pricingPeriod owns each schedule; date-derived labels alone are insufficient for clipped/legacy periods.
4. Long-term needs one canonical Normal availability range starting on its real saved date with endNULL, plus a validated versioned recurring Normal price rule analogous to existing recurring Campaign. Store both Normal half prices and market/original amounts in that rule. Do not create unbounded future months, sentinel expiry dates or a new schedule/cron. The canonical base range governs lifecycle and range coverage; it is not a second editable source for the rule's resolved selling price. Define and validate base-price consistency with the first-half rule, and derive effective current prices centrally.
5. Shared effective-price precedence: active selected Campaign event overrides the monthly Normal half; otherwise days1–15 use first-half Normal and days16–month-end use second-half Normal. Uniform mode uses one price. Reject overlapping Campaign definitions or resolve them through the existing validated event model. Use owning-store timezone, canonical market/currency and integer minor-unit arithmetic.
6. Recurring Normal bounds must fit saved package availability and share its start/end semantics. Existing recurring Campaign validator assumes exactly one Normal row; adjust it deliberately for finite split ranges while proving full continuous Normal coverage. Long-term canonical single-range restriction remains appropriate. Ordinary End must terminate Normal rule, Campaign rule and concrete price bounds; no ended view/rule may remain Ongoing. Preserve active-package start-date lock.

## Approved design amendment — canonical availability plus Normal rule for every duration

The simpler proposal is **ACCEPTABLE and preferred**: BOTH finite and long-term packages retain their existing canonical Normal availability rows, while `_normalMonthlyRule` schema1 contains per-market early/late Original/Selling prices with no independent dates. This supersedes the earlier recommendation to physically split finite Normal rows or maintain a schedule-to-half mapping. Availability alone owns package start/end; the price rule cannot extend it. Read-only UI/History/Sheet projections may show clipped half-month segments, but must never become a second editable price source. Existing row count, overlap, lifecycle and start-lock behavior can therefore remain stable.

`app/pricing-periods.ts` was inspected during development. The explicit mode and period keys, positive two-decimal rule validation, market matching, and canonical early-price consistency are aligned with the design. Every effective-price/preview/Sheet consumer must apply rule prices only inside a currently eligible canonical Normal interval, then let active Campaign pricing override Normal. `resolvedNormalPrice` currently relies on caller availability checks; make this contract explicit. `readNormalMonthlyRule` is currently lenient (returns null for invalid/missing schema, shallowly accepts prices), so save/reprice must validate and unsupported/invalid split-mode stored data must surface a clear error rather than silently reverting to one baseline price. This is design approval, not final approval of these still-changing implementation paths.

Export API inspected: inserts omit physical schema_version, preserving default1. New `snapshotAmounts` includes payload pricingSchemaVersion2/mode and scenarios retain explicit pricingPeriod; request fingerprint covers the payload. This satisfies the current database CHECK and immutable snapshot contract without any DDL. Existing two-scenario payloads remain legacy content, and new mode/period changes require fresh immutable export references or conflict on reused request IDs. No database or business writes performed by reviewer.
